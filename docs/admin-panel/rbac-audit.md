# RBAC audit — Phase 0

Produced by reading the router, the middleware and the policies, then probing a
running backend with a real `VIEWER` token. Nothing below is inferred from a
design document.

**No implementation was done in this phase.** One backend defect was found and
is reported, not fixed.

---

## 1. The headline finding — **FIXED**

Closed by `fix(auth): enforce operational tiers on driver-shared endpoints`.
Verified against the live backend with database state, not status codes:

```text
              complete a running trip      trip state after
VIEWER        403                          RUNNING
SUPPORT       403                          RUNNING
OPERATIONS    200                          COMPLETED
DRIVER        200  (their own trip)        COMPLETED

              raise incident   add note
VIEWER        403 (count 1→1)  403
SUPPORT       201 (count 1→2)  201
```

The original finding is kept below because it is why the tests exist.

> **A `VIEWER` completed a running trip.**

```text
POST /api/v1/trips/{id}/complete    with a VIEWER token    → 200

trip status now: COMPLETED · ended_by set: True · actual_arrival: 09:40:23
```

That is not a permissive status code. The bus's run was ended, the arrival was
stamped, and the account that did it exists for read-only oversight.

The same account also reached:

```text
POST /trips/{id}/start              → 409  (authorised; refused by a business rule)
POST /trips/{id}/board              → 422  (authorised; refused by validation)
POST /trips/{id}/positions          → 409  (authorised)
POST /trips/{id}/stops/{id}/arrive  → 404  (authorised; bad stop id)
POST /incidents                     → 201  (created)
POST /incidents/{id}/notes          → 201  (created)
POST /incidents/{id}/cancel         → 422  (authorised)

control, correctly gated:
POST /incidents/{id}/acknowledge    → 403
```

A 409, 422 or 404 here means **authorisation passed** and only payload or state
stopped the request. The control proves the probe distinguishes the two.

### Why G3-1 and G3-2 did not catch it

Both earlier fixes worked on routes that carry `RoleAuthorize:ADMIN`. This
family carries **no role gate at all**, because the same endpoints serve the
driver app — the assigned driver must reach them from a bus. Their policies then
say `isAdmin()`, which every administrator satisfies.

`TripPolicy::operate` states the intent in its own comment:

> *"Starting and ending are the assigned driver's job; operations can act on
> their behalf when a driver's device has failed."*

Operations. Not oversight. The implementation says any admin.

**Classified G3-3. FIXED — see §6.**

## 3. Current admin-panel RBAC gaps

The architecture is sound; the coverage is thin because slices 2–5 are
read-only.

**What exists and works**

- `AccessLevel` enum with `meets()` — the backend's `atLeast()` ladder, never a
  string comparison
- `CAPABILITY` map, `can(capability)`, `hasAccess(level)` on the session
- `RequireLevel` route guard rendering `Forbidden`, never redirecting to login
- Navigation filtered by level; sections absent rather than disabled
- The shell renders nothing until the level is known, so no authorisation flicker
- `/auth/me` is the single source of the level

**Gaps that matter for the operational phases**

| # | Gap | Consequence |
|---|---|---|
| F1 | `CAPABILITY` is hand-written, 28 entries | Will drift from the router. Must be generated from `capability-map.json` |
| F2 | Only one capability is used in anger — `trip.correct` | Nothing else is gated because nothing else mutates yet |
| F3 | Access level is read once at boot | An operator demoted mid-session keeps the old tier until reload — §21 of the brief |
| F4 | No capability metadata on routes, only a minimum level | A screen can be reachable while every action on it is forbidden, with no way to say so |
| F5 | No shared mutation shell | Confirmation, in-flight disabling, 409-verbatim and 422-to-field are re-implemented per call site today |
| F6 | `Forbidden` exists but no per-action forbidden state | An action that 403s anyway has no consistent surface |
| F7 | No capability tests | The four-tier matrix is asserted against the backend, never against the UI |

## 6. Backend changes required

### G3-3 — driver-operational endpoints admit any administrator

**Severity: high.** Proven, above.

**Endpoints.** `POST /trips/{id}/start`, `/complete`, `/positions`, `/board`,
`/alight`, `/stops/{stopId}/arrive`, `/stops/{stopId}/skip`, `/left-behind`,
`POST /buses/{id}/inspections`, `POST /incidents`, `/incidents/{id}/notes`,
`/incidents/{id}/cancel`, `POST /evidence`.

**Why route middleware cannot fix it.** These are shared with the driver app. A
blanket `access:OPERATIONS` would stop the assigned driver starting their own
bus — the primary use of the endpoint. The shape is identical to G3-2, which
was fixed in the policies, and the same remedy applies:

```php
// TripPolicy::operate
if ($actor->isDriver() && $actor->driver?->getKey() === $trip->driver_id) {
    return true;                                   // the assigned driver
}

return $actor->hasAccessLevel(AccessLevel::OPERATIONS);   // standing in for them
```

The docblock already says "operations can act on their behalf"; this makes the
code say it too.

**Policies affected.** `TripPolicy::operate`, `VehicleIncidentPolicy::create`
and `::cancel`, the note authorisation on `IncidentController::addNote`,
`EvidenceFilePolicy::create`, and the inspection store path.

**Proposed tiers**

| Action | Subject exception | Tier |
|---|---|---|
| start / complete / board / alight / arrive / skip / left-behind / positions | the assigned driver | OPERATIONS |
| record inspection | the driver of that bus | OPERATIONS |
| raise incident · add note · attach evidence | any driver | SUPPORT |
| cancel incident | the reporter | SUPPORT |

Raising an incident and adding a note stay at SUPPORT deliberately: a system
that makes somebody wonder whether they may report an emergency has already
failed, and `VehicleIncidentPolicy` says exactly that.

**Implemented.** `TripPolicy::operate` now asks for the assigned driver or
`OPERATIONS`; `VehicleIncidentPolicy::create` and `::cancel` for a driver or the
reporter, else `SUPPORT`; `EvidenceFilePolicy::create` for a driver else
`SUPPORT`; `VehicleInspectionController::resolveInspectingDriver` for
`OPERATIONS` when an administrator stands in.

`IncidentController::addNote` authorised `view`, so reading an incident carried
the right to write on its record. It now authorises a new `addNote` ability —
changing `view` would have broken every read.

18 tests in `DriverOperationBoundaryTest`, including a mechanical sweep that
fails if any trip mutation admits a VIEWER. 1098 → 1116, none removed.

**One ordering note discovered while testing.** For endpoints using a
FormRequest, validation runs before the controller reaches its policy, so an
unauthorised caller sending an invalid payload sees 422 rather than 403. The
authorisation is still enforced — it is simply not the first thing to refuse.
The tests send valid payloads for exactly this reason.

### No other backend change is required

Every workflow in §5 is served by an existing endpoint at a coherent tier. No
new endpoint, field, or business rule is needed for the operational panel.

## 7. Required frontend architecture changes

| # | Change | Replaces |
|---|---|---|
| A1 | Generate `CAPABILITY` from `capability-map.json` at build time | 28 hand-written entries (F1) |
| A2 | A capability id per operation, each naming its endpoint | Ad-hoc strings |
| A3 | Route metadata carries `capability` as well as `minimum` | F4 |
| A4 | Re-read `/auth/me` on window focus and after every 401 refresh; adopt the server's level and re-evaluate the current route | F3 |
| A5 | One `useOperation()` mutation shell: confirmation, in-flight lock, 409 verbatim, 422 to fields, 403 to the forbidden surface, form state preserved on failure | F5, F6 |
| A6 | `<Capability>` guard for action surfaces, mirroring `RequireLevel` for routes | F2 |
| A7 | A generated four-tier test matrix asserting navigation, route access and action visibility | F7 |

**The rule that does not change:** none of this decides anything. It decides
what to *offer*. The server decides what happens, and a 403 arriving anyway is a
bug in the map — which is why the map is generated from the router.

## 9. Test strategy

Three layers, none of which substitutes for another.

1. **Capability unit tests.** The generated map against the committed
   `capability-map.json`: every mutation the panel offers names a real endpoint
   at the tier the router enforces. Fails if the backend moves.
2. **Component tests, MSW.** Per workflow per tier: is the action offered, is it
   absent, does a 409 render verbatim, does a 422 reach the field, does a 403
   render the forbidden surface without logging anybody out.
3. **Real-backend authorisation tests.** For every mutation: correct tier
   succeeds, lower tier 403s, unauthenticated 401s. This is the layer that
   caught G3-3 and the layer MSW can never replace.

Plus a generated matrix test asserting navigation and route access for all four
tiers — the table in §5, executed rather than written down.

**Browser verification remains unavailable.** The Chrome extension has been
disconnected since Slice 2. API-level verification is not visual verification
and is not reported as such.
